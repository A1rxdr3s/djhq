# Invitation-only identity enforcement: feasibility proof

**Decision: FEASIBLE, NOT PROVEN.** No provider-backed tests were performed. Public signup activation is **no-go** until the isolated tests below pass. This supplements [DJHQ multi-product HQ architecture](./DJHQ_MULTIPRODUCT_HQ_ARCHITECTURE.md); it does not supersede its route decisions or implement authentication.

## Verified repository boundary

- `app/sign-in/page.tsx` calls Supabase Google OAuth and email `signInWithOtp`, with no `shouldCreateUser: false`; email is presented as a magic link. `app/auth/callback/route.ts` defaults to `/hq`, does not check exchange errors, and uses `next` without an internal-path allowlist. Neither is changed here. Live provider configuration and signup status are unknown.
- `lib/supabase/server.ts` provides SSR cookie sessions. `app/hq/page.tsx` verifies `getUser()` and finds artists by `owner_user_id`; `app/account/page.tsx` checks the user without requiring an artist. Preserve existing users, IDs, sessions and artist relationships.
- `supabase/migrations/047_admin_invitations.sql` defines a separate artist/admin invitation with raw token and URL; `app/invite/[token]/page.tsx` has disabled acceptance. It is not the proposed product invitation. No product-grant mechanism was established by inspected schema/routes. Set2Go authorization is outside this proof.

## Candidate designs

| Design | Admission boundary and assessment |
| --- | --- |
| Before User Created hook with email or user metadata | Supabase documents a pre-creation rejection hook, but its documented event has user and request metadata, not a proven trustworthy invitation transaction binding. Client `user_metadata` is forgeable; an email-only open admission window can be raced. Do not deploy this as the gate until a provider-specific trusted binding and transaction behavior are demonstrated. [Hook documentation](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook). |
| Disable public signup; privileged provisioning after independent identity verification | **Recommended experiment.** Supabase documents a global signup restriction and server-only `auth.admin.createUser`. DJHQ first verifies an identity outside a newly created Supabase account, binds it to a valid invitation, then the trusted server provisions only that verified identity. Existing Auth users sign in normally. Crucially, test that the actual configured provider rejects new OAuth and email users and that admin provisioning works with signup disabled and any hook enabled. [Signup configuration](https://supabase.com/docs/guides/auth/general-configuration), [admin createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser). |
| External identity broker / another provider | If Supabase cannot safely support the provision-and-link flow, choose an identity system with an authenticated pre-creation admission context. This is a separate architecture decision, not a product-grant-only substitute. |

The candidate is not a claim that `createUser` followed by Google linking works with this project. It adds a trusted pre-verification service, Google OAuth configuration and email OTP delivery, so operational cost and duplicated provider flows are real tradeoffs. If preserving native Supabase OAuth as the *first* step is mandatory, the hook's unproven invitation binding remains a blocker. No new email allowlist window may be opened.

## Proposed lifecycle and trust boundaries

1. `/admin` creates a product invitation with a random 256-bit bearer token, hash-only storage, expiry, revocation and optional normalized email binding. A DM link is unbound: whoever holds it may claim it; possession is not proof of a particular Instagram identity. Opening the URL never consumes it.
2. On opening, validate only enough to start a short-lived server-side registration transaction; place an opaque random transaction reference in a `Secure`, `HttpOnly`, host-only, `SameSite=Lax` cookie and remove the original token from the address bar. Store only hashes of bearer secrets, exclude URLs and secrets from logs/analytics, use `no-store` and restrictive referrer policy. Recheck status at every privileged transition; scanners opening links must not burn or reserve invitations.
3. **Google path:** a dedicated server-controlled Google OIDC flow verifies signature, issuer, audience, expiry, nonce and `email_verified` and binds verified `(issuer, sub)` and email to the invitation transaction. OAuth state and PKCE are unique, single-use and bound to the transaction; do not trust client metadata, arbitrary email or the callback URL. This requires its own approved Google client configuration. A forwarded unbound link can legitimately be claimed by its holder; a mismatched verified Google email cannot claim a bound invitation.
4. **Email path:** before creating any Supabase Auth user, a separate server-controlled six-digit email challenge verifies mailbox control and binds the verified email to the transaction. It needs cryptographically secure codes, keyed hashing, short TTL, strict atomic attempt limits, resend/rate controls, one-time consumption and generic responses. It is **not** the existing Supabase OTP signup flow: that flow may create a user before code verification. After provisioning, normal Supabase email OTP sign-in for existing users is a separate step. [Supabase email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless).
5. A DB transaction locks the invitation and rechecks token binding, expiry, revocation, email match and unused status; atomically claims it for one verified identity and creates a durable provisioning record. Unique constraints on invitation, identity and grant prevent concurrent double-claims. A privileged server provisions the Auth identity, using only verified identity data and no password; the service credential stays server-only. Never infer email verification from user-supplied input. Verify whether a pre-confirmed email is appropriate only after independent verification.
6. Supabase Auth admin creation is a remote operation and **cannot be assumed atomic with the application DB transaction**. Use a durable idempotent saga: claimed → provisioning → provisioned → grant active, with an exclusive lease, unique idempotency record, retries and reconciliation. A crash after Auth creation must discover the exact created user and finish safely, never create another or grant by email alone. A revoked or expired invitation before claim fails; policy for revocation after claim and failed provisioning requires explicit definition. No product grant until identity and provisioning are reconciled. Existing Auth account collisions require authenticated proof of control of that exact existing user; never blindly adopt by matching email, especially for artist/admin accounts. Keep grant issuance separately transactional and unique.
7. Establish a real Supabase session by a tested supported path: email OTP for the provisioned user, or Google OAuth only if isolated tests demonstrate safe linking to the same verified user. Do not issue a homemade Supabase session. After session validation, grant and owner checks, redirect to `/set2go`. Existing artists continue their existing sign-in without invitation; test that disabling signup and any hook do not disrupt their session refresh, `/hq`, or linking. The independent first-time verification may add an extra sign-in step; UX must disclose it.

## Abuse and failure cases

- Invalid, expired, revoked or already claimed tokens fail without account creation; race the claim in the database, not application memory. Bound-email mismatch fails before provisioning. Generic errors prevent unnecessary enumeration.
- A stolen DM URL is a bearer claim opportunity; protect tokens in transit and storage, and offer revocation. Browser flags and unverified metadata never authorize creation.
- OAuth callback failure or interrupted verification leaves no claimed invitation; after claim, resume the same durable transaction and reconcile rather than release it unsafely. Replayed OTP/state/nonce is rejected. Strict per-IP and per-account limits and monitoring are required.
- Existing-user login must use the provider's verified identity/session; do not bypass a signup gate based on an attacker-supplied existing-user flag. Account linking and normalized-email collision policies must be tested against real Supabase behavior.
- `next` must be a server-allowlisted relative internal path; reject external, protocol-relative, encoded and control-character variants, then reauthorize the destination. Preserve artist login separately. Never send invitation tokens in Google `state`, callback URLs, referrers or query logs.

## Evidence and reproducible provider test

On 2026-11-01, `node --test tests/invitation-admission-model.test.mjs` passed 13 tests. This is an in-memory simulation: provider labels and verified identities are assumed, and synchronous check-and-set is not a database concurrency test. It proves no Supabase account-creation enforcement, OAuth verification, OTP behavior or transaction isolation.

Supabase CLI exists; no `supabase/config.toml` or Docker executable was found. No isolated environment or permission to configure one was confirmed. No hosted project, users, OAuth configuration or production settings were changed. The smallest missing prerequisite is an explicitly designated disposable Supabase environment with permission to configure Auth; Google-path proof additionally requires a test Google OAuth client and test accounts, and email-path proof a test mail sink/provider. Local service startup or cloud provisioning requires separate authorization.

In that isolated environment, record versions, settings and Auth user counts before and after each test without storing tokens or secrets. Test: direct uninvited Google and email API creation with signup disabled; authenticated existing artist login and refresh; authorized provision under disabled signup; admin-create behavior with hook enabled and fail-closed hook failure; Google identity linking to the same pre-provisioned user; OTP delivery, verification, replay and expiry; wrong verified identity; invalid/expired/revoked/reused invitations; two genuinely simultaneous DB transactions; interrupted provisioning at each boundary and idempotent reconciliation; collision with existing user; redirect manipulation; no grant or `/set2go` access before authorization. Exercise link forwarding and scanner prefetch. Capture actual errors and assert zero unexpected Auth users, grants or changes to artist records. Verify test isolation before any privileged action.

## Implementation gate

1. Approve an isolated test environment and independently verified identity approach, including whether an additional initial verification/login step is acceptable.
2. Prototype provider configuration and external verification, then run the negative and recovery tests above; investigate whether admin provisioning is compatible with global signup restrictions and hooks.
3. Only on success, design production schema, restricted administration, server-only credentials, rate limiting and operational reconciliation; separately authorize changes and test existing artist routes.
4. Implement product-grant and Set2Go job ownership checks separately. Do not activate public signup until provider-level proof, authorization and release checks pass.
