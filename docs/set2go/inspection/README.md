# Restricted inspector: review before provisioning

Do not execute `create-role.sql` on hosted infrastructure until an administrator has audited effective PUBLIC privileges and approved the change. It creates a NOLOGIN role with no password or explicit grants. PostgreSQL catalogs are generally visible without table data privileges, but visibility varies by managed configuration. Inspecting rows of `supabase_migrations.schema_migrations` is not a catalog query and requires separately authorized SELECT; migration 082 status cannot be established by this role as proposed. Function bodies and protected metadata may likewise be unavailable. Never grant broad data access merely to close these gaps.

PostgreSQL commonly grants PUBLIC CONNECT, TEMPORARY, function EXECUTE, and potentially schema USAGE/CREATE or application privileges. Actual grants, inherited memberships, SECURITY DEFINER functions and extensions must be audited in the existing database before enabling LOGIN. NOINHERIT alone cannot remove privileges granted to PUBLIC. A dedicated login cannot be made safe by revoking PUBLIC privileges only from that role, and changing existing PUBLIC grants affects existing applications: stop and assess separately if unsafe effective access exists. Read-only transaction defaults are not a security boundary. Inspect effective SELECT/INSERT/UPDATE/DELETE, schema CREATE, database TEMPORARY and EXECUTE privileges, including role memberships and overloads, before activation. Treat privileged functions exposed via PUBLIC as possible mutation paths even if table writes are denied.

After approval, use the SQL Editor to create the disabled role; provision a strong password through a secure administrative client using `psql`'s `\\password djqh_schema_inspector` prompt, not a SQL file, command-line argument or chat. Enable LOGIN only after checking effective privileges and password provisioning. Managed-role restrictions and pooler support for custom roles must be verified first. Never use the administrative role as the ongoing inspector.

Install an appropriate PostgreSQL client only with approval; `psql` was not found locally. Obtain the exact direct or session-pooler host, port and project-specific username from the Supabase Connect dialog. Direct access normally requires IPv6; use the session pooler for IPv4. Do not infer the pooler hostname. Keep connection parameters in a separate Git-ignored `.env.local`-style private config or a local `~/.pg_service.conf` with mode 0600; store the restricted password in a mode-0600 `~/.pgpass` or use an interactive prompt. Do not place connection URIs or passwords in shell history. Use TLS certificate verification as supported by the project, with a trusted CA. Run `psql -X -v ON_ERROR_STOP=1 -f docs/set2go/inspection/metadata.sql` with connection parameters supplied privately.

The metadata script makes no application-table queries; it reports effective privileges for selected objects and RLS flags. A successful connection proves neither lack of all mutation paths nor that every required catalog is visible. Inspect all effective PUBLIC function EXECUTE and schema privileges with an appropriately authorized administrator. Negative write/SELECT tests must run only in a disposable environment; on hosted infrastructure use privilege inspection without executing data reads or writes. The intended checks include protected-table SELECT/INSERT/UPDATE, function EXECUTE, schema CREATE, database TEMPORARY, and membership in privileged roles. No role or live database changes have been made by these files.
