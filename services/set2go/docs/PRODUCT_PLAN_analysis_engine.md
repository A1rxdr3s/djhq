# Product plan: musical analysis engine (phase started 2026-10-29)

Goal: reliable BPM, beats, downbeats, key/Camelot, with interpretable confidence signals and manual corrections. Mixed In Key (MiK) is a comparison reference only; no claim of equivalent accuracy. Opt-in: nothing here is imported by the export path; the stable export baseline (desktop_v18_consolidated), waveform algorithms and production defaults are unchanged. Deferred: mobile, RGB/3Band, energy, phrase detection, automatic cue suggestions.

Free-software obligations vs commercial options: GPL/AGPL components (libKeyFinder GPL-3, Essentia AGPL-3 code, also mutagen GPL-2+ in the main environment) are COPYLEFT: they allow commercial use but bind a distributed (AGPL: also network-served) combined work to offer its source under the same licence; a commercial licence is an option, not a requirement. CC BY-NC(-SA/-ND) MODEL licences (madmom models, Essentia's MTG models) forbid commercial use outright. Algorithms are assessed separately from weights. Nothing in this phase needs a purchase. For a future commercial/server distribution these must be revisited per component (the project's own distribution licence has not been decided).
Practical recommendation: DEFAULT beats/downbeats = Beat This! (MIT, already hardware-validated; CPU 5-7 s/track). Fallback = the Fourier tempogram + kick-refined grid (no model). KEY: keep libKeyFinder as the baseline and add an independent in-house estimator (published Krumhansl-Kessler / Temperley profile tables over peak-picked chroma; no third-party code, no licence issue) as a SECOND OPINION that feeds confidence, not as a replacement. Future server use: Beat This! runs on CPU/GPU in a worker (peak RSS ~1 GiB per model process measured earlier); GPL libKeyFinder is the main licensing question for distribution.

## Implemented in this phase (src/set2go/analysis/, scripts/analysis_eval.py; opt-in)
- metrics.py: BPM error with octave classes (exact/half/double/3-2/2-3/other); beat timing (offset at start/middle/end thirds, drift, F-measure with a window < half a beat so a whole-beat shift is never matched as correct); downbeat bar-origin shift and per-segment agreement as a quantity SEPARATE from tempo and timing; intrinsic downbeat stability.
- keys.py: parse/name/Camelot (matches the existing 24-key map exactly), relation classes (exact / parallel / relative / fifth / semitone / other, never folded into exact), peak-picked chroma + profile correlation with interpretable signals (margin to runner-up, parallel-mode gap, tuning).
- refs.py: kinds of evidence kept apart (tag = candidate, official rekordbox = comparison, user = labelled, MiK = comparison); sha256 identity; development vs independent split.
- review.py: needs_review reasons with the measured value and the limit; no probabilities.
- sidecar.py: hash-linked, GRIDS.json-compatible; raw runs appended per analysis version; manual bpm/anchor/bar_origin/key with provenance (who/when/analysis version/note); re-analysis preserves manual; changed audio => stale (old state kept, overrides not applied to the new audio).
- Tests: 21 new (metrics, keys, sidecar, review); 111 total pass. The chroma estimator is validated on 48 synthetic cases (24 keys x 2 detunings) and recovers a +30 cent detune as 30.1; a first version failed that test (17/24 wrong) and was rewritten before use.

## Initial measured results (10 development tracks; see HANDOFF.md and eval/analysis/run_dev_baseline.json)
There are NO user/MiK labels yet and NO independent tracks: every number below is on development tracks and against tags (candidates) or the 3 official rekordbox analyses (comparison). No generalisation is claimed.
- BPM: Fourier tempo agrees with the tag BPM (8 tags present) within 0.005 BPM and with the official analysis on 3 tracks; no octave errors. Agreement with tags is not independent proof (tag origin unknown).
- Beats vs official (3 tracks): constant offsets +14.8 / +7.4 / +15.5 ms (est - official), drift +0.0 / +0.3 / +0.0 ms, F(70 ms) 0.998-0.999 (same offsets as the earlier hardware-validated record, opposite sign convention).
- Downbeat vs official (3 tracks): bar origin correct on all three, 94-100% per quarter.
- Downbeat stability (all 10): every minority run is exactly 2 beats (half a bar) off, in contiguous blocks (e.g. 14 bars on "Also!", 8 on Chris Valencia, up to 4-6 on Ritmo). Only on "Also!" and Chris Valencia do these blocks coincide with low-kick bars (minority kick 0.24x / 0.55x the median bar vs 1.10x / 1.34x in the majority); on Habit, Ritmo and Earth the minority bars have NORMAL kick energy (0.98 / 1.01 / 1.11 x) so a breakdown explanation is NOT supported there: at least two failure causes.
- Key vs tag (tag = candidate): libKeyFinder exact on 5/10 (the other five: Zsak parallel mode, Habit fifth, Chinonegro fifth, Alex Preston semitone, Ritmo other); the new chroma/Krumhansl estimator exact on 4/10 and agrees exactly with libKeyFinder on 6/10; the two disagree with each other and with the tag on Zsak (both say D major vs tag D minor: a REAL parallel-mode question that needs a human or MiK value), Habit (both 8A vs tag 7A), Ritmo (both 3A vs tag 1A). Where two independent estimators agree with each other against the tag, the tag is the one to question; this is a flag, not a verdict.
- Runtime/memory: key estimators 0.5 s (libKeyFinder) + 0.4 s (chroma) per track; whole 10-track evaluation 31 s with cached Beat This! predictions. Peak RSS 3.9 GiB, caused by the EXISTING `bpm_detect._onset_envelope` (about 2.3 GiB for a 6-minute track) and tempo scan (+0.2 GiB); the new analysis code adds < 400 MiB (libKeyFinder ~330 MiB). Not changed in this phase; matters for server use.

### Opt-in key workflow (`src/set2go/analysis/workflow.py`, `scripts/analysis_key_workflow.py`; default exporter unchanged)
- Layers kept apart: IMPORTED (existing Mixed In Key payload/tag, explicit provenance, "reading metadata, not detection"), PREDICTED (named methods: libKeyFinder + Essentia bgate/edma/edmm/braw, frozen configuration, audio only), MANUAL (hash-linked sidecar). Effective key = manual > imported; predictions are NEVER promoted automatically, so a track with no stored/manual key has NO effective key (PDB key_id 0).
- Review reasons (descriptive, no probabilities): no key available; stored fields conflict; unknown-origin tag; predictions differ from the effective key (fires if ANY method differs; the detail lists each method's relation); methods disagree on MODE; method FAMILIES disagree on the TONIC; method failed. Agreement is reported as "families agree: not evidence of correctness". Same-family profiles count as one family.
- Re-analysis (`reanalyse`) appends a run record, keeps manual overrides, and retires them as stale (kept under "stale") when the audio hash changes; an override for different audio is not applied in the export map.
- Manual correction: `grid_tool.py key|key-clear`. Opt-in export: `export_library(..., effective_keys=map)`; `verify_export.py --effective-keys=<map.json>` accepts exactly the mapped keys (null = must have none) and only for the listed tracks; a wrong map entry still fails. Verified on the real PDB (Zsak: manual 10B replaces imported 7A in the KEYS table and in the track's key_id; every other track-row field and every other file identical to frozen v18 except export.pdb; key_id NUMBERS of other tracks shift because ids follow first use, their key NAMES are unchanged). Default export after the change: byte-identical to frozen v18.


## Update 6: opt-in prediction policy and the end-to-end key command (2026-10-29)
Problem: tracks without stored metadata had no effective key. Solution (opt-in; default behaviour unchanged): `layers.resolve_key(..., policy={"backend": "<label>"})`.
Precedence: 1 valid manual override > 2 valid imported annotation > 3 the prediction of the EXPLICITLY selected backend > 4 no key (backend failed, returned nothing, or the input is unsupported). With policy None predictions are never promoted. A manual or imported value that does not parse as a key is INVALID: skipped (reported under `invalid` and as a review reason), never shown as the effective key, so the next layer applies.
Initial backend: libKeyFinder (label with the REAL installed version, e.g. "libkeyfinder 2.2.8"), chosen for availability and simplicity, NOT because it is the most accurate: the evaluation sets show it leans minor and is weakest on tonic. Essentia stays advisory (isolated worker; refused as a policy backend); the tonic/mode hybrid is not implemented.
Labelling: a predicted effective key carries backend and version in the key map, in the sidecar run record (policy, selected prediction, failures) and in a review reason ("key is a PREDICTION from <backend>; not verified, accuracy not established"). Disagreement between methods adds reasons and never replaces a manual or imported value. A CLEAN review output only means no ran-method disagreed: it depends on which predictors ran and is not verification.
Command: `scripts/analysis_key_export.py <out_dir> <files/dirs> --sidecar <sidecar.json> [--predict libkeyfinder] [--essentia] [--playlist N] [--analysis-from D --link-audio-from D] [--dry-run]`: analyse -> hash-linked sidecar (raw runs appended, manual preserved, stale detection) -> `<out>_KEYS.json` -> local export through `export_library(effective_keys=...)`. It refuses an unsupported backend, a non-empty output directory and a too-small disk, prints failures, and exits 1 if a file failed.
Limitations: libKeyFinder's accuracy is unestablished (mode-dependent errors); no confidence value exists; the policy backend is a single method (no ensemble); a prediction is only as good as the audio (silent or very short input gives no key); full analysis of new tracks costs ~4 s and ~1 GiB per track and the export copies audio (use --link-audio-from for known tracks); the exporter does not call the workflow by itself; the default export never reads the sidecar.


## Update 7: arbitrary-source verification via a source manifest (2026-10-29)
Gap closed: `verify_export.py` resolved its sources from a hardcoded `test-tracks/`, so exports built from other folders could not be fully verified. Now `analysis_key_export.py` writes `<out>_MANIFEST.json` (module `analysis/manifest.py`) and `verify_export.py --manifest=<json>` takes sources, playlists, destinations, device paths and expected keys from it. Without `--manifest` the verifier is unchanged: v18 output is identical line for line (217 checks) before and after.
Manifest per track (playlist order kept; one track may appear in several playlists): source resolved path + sha256 (identity; the basename is NOT an identity), destination `Contents/<basename>`, device path (what the PDB and both PPTH sections must contain), expected key {camelot, name, origin manual|imported|predicted, backend, provenance} or null, key layers at export time.
Duplicate basenames: the export's destination is `/Contents/<basename>`, so two DIFFERENT files with one basename cannot coexist; the CLI refuses with exit 2 naming both paths and hashes, before any analysis or sidecar write. The same file selected twice (same resolved path) is collapsed and reported; identical bytes under different names stay two tracks and are noted.
Verifier checks in manifest mode: source still has the manifest sha256 (detects edits after export), destination hash == manifest hash == source, playlist membership and order by device path, PDB track set == manifest set, key row == manifest expected key (null = must have none) with origin/provenance printed, PDB analyze_path, DAT PPTH and EXT PPTH == manifest device path, ANLZ structure, strict file set (--exact).
Two verifier adjustments, manifest mode only (v18 path untouched): PQTZ minimum scaled to the duration (>= one beat per 2 s, ascending and distinct) instead of a fixed 100 beats; a uniform PWV4 is accepted ONLY when the decoded source is exactly zero (measured from the audio, never inferred from the key).
CLI hardening: argparse with `allow_abbrev=False`; unknown flags, `--predict essentia`, `--analysis-from` without `--link-audio-from` (and vice versa), missing sources, unsupported file types, missing `--sidecar`, a non-empty output directory and a too-small disk all fail with exit 2 and a message (the old CLI silently ignored unknown flags: a stray `--rhythm` had passed unnoticed). Export failures print an error, say the partial output must not be used, and write no manifest.
Policy and algorithms unchanged: prediction stays opt-in (`--predict libkeyfinder`), libKeyFinder's accuracy is not established, no Mixed In Key-level accuracy is claimed.

## Update 10: experimental opt-in revision of the rejected-grid decision (2026-10-29)
`set2go.analysis.gridcheck` (production gate unchanged, not wired into any CLI): decides rejected-grid cases from the beats and the AUDIO-derived tempo, separating beat-count/slope artefacts (beats still on one grid) from real drift or tempo change: slot fit and coverage, windowed phase, contiguous missing runs, and an explanation rule that requires identified local count errors. ## Update 11: gridcheck count-explanation (direction + magnitude), duration-aware drift budget, and reproducible runner (2026-10-29)
- **Count-explanation rule (`set2go.analysis.gridcheck`):** Over beat span `span`, the signed beat-count discrepancy implied by `slope - tempo_bpm` against the audio tempo is `implied_diff_signed = count_model - count_audio = span * (slope - tempo_bpm) / 60` (correcting the earlier `count_model - count_actual` which subtracted an interval count that already included the count errors). In OLS regression of beat time on beat index over `[0, N]`, a local count change `dN` at relative position `u in (0, 1)` shifts the slope-implied beat count by `6*u*(1-u)*dN` (same sign as `dN`; leverage `1.5` at midpoint `u=0.5`, `1.0` for uniform spread, `>=0.54` across `u in [0.1, 0.9]`). Extra beats from short intervals (`<0.6*own`) are counted per contiguous short-interval run as `max(len(run) - round(sum(ibi[run]) / per), 1)` so a 50/50 split of one period into two half-beat intervals counts as `+1` extra beat (not `+2`: Eyes Low's 17 short intervals across 9 split periods now report `+9` extra beats, not `+17`). A slope gap `> 0.25 BPM` is explained only when the audio-indexed ramp is small AND `local_net = split - skipped` has the **same sign** as `implied_diff_signed` AND `0.5 * |implied_diff_signed| <= |local_net| <= 2.0 * |implied_diff_signed|` (with `|local_net| >= 1` and `|implied_diff_signed| >= 0.5`). A large absolute count alone cannot establish an explanation; opposite-sign or out-of-range counts return `needs_review`.
- **Duration-aware tempo/drift criterion:** Reserving one full Beat This! frame (`MODEL_FRAME_MS = 20.0` ms) for local quantisation/jitter inside `MAX_WINDOW_OFFSET_MS = 35.0` ms bounds the one-sided displacement at each end of a median-anchored grid to `15.0` ms, or `MAX_TOTAL_DRIFT_MS = 30.0` ms end-to-end across track duration `duration_s` (matching `rhythm.MAX_BEAT_RESIDUAL_MS = 30.0` ms and keeping end beats with `+-20` ms frame error within `FIT_MS = 40.0` ms so inliers are not clipped). The ramp limit is `min(25.0, 30.0 / (duration_s / 60))` ms/min, corresponding to a maximum tolerable tempo error of `tempo_bpm * ramp_limit / 60000` BPM (`0.0128 BPM` on a 5 min 128 BPM track, catching `0.02 BPM` drift where `fit == 1.0` and `bad_windows_s == []`). Tradeoff: a `0.005 BPM` tempogram step passes on standard 5 min tracks (`~11.7` ms drift at 128 BPM) but is **not** assumed to always pass — on tracks longer than `6 * tempo_bpm` seconds (`~12.8` min at 128 BPM, `12.0` min at 120 BPM) a `0.005 BPM` error exceeds `30.0` ms and returns `needs_review`.
